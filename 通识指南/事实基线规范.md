# 通识指南 · 事实基线规范

> **每个模块开写前必读。**
> 这个模块的事实密度是四个模块里最高的——年份、数字、法条、机构名、参数，一样错就是硬伤。

---

## 一、为什么要有这份规范

前车之鉴（`观万部影` 两批的真实数据）：

| 批次 | 篇数 | 审稿问题 | 每篇 |
|---|---|---|---|
| 第一批 | 125 | 109 | 0.87 |
| 第二批 | 75 | **195** | **2.6** |

第二批错误率是第一批的 **3 倍**，根因只有一个：**事实基线给得太粗，agent 只能靠记忆补，补不上的就编。**

典型错误：
- 把《终结者 2》的结尾旁白安到第一部头上
- 把《美国往事》的现在时说成 1980 年代（片中为 1968）
- 把摄影指导写成只拍了废掉那版的人

**电影情节记错，读者可能发现不了；但"某国议会多少席""某条款第几条""某年GDP多少"记错，是一查就穿的硬伤。**

## 二、事实基线是什么

**每个一级模块建一份 `事实基线.md`，写卡片之前先写它。**

它不是知识卡片，是一张**"这个模块里最容易记错的硬事实"清单**：

```markdown
# <模块名> · 事实基线

> 本文件只列硬事实，不做解释。卡片写作时**只引用本文件，不自行生成**。

## 一、关键年份
| 事件 | 年份 | 备注 |
|---|---|---|
| …… | …… | …… |

## 二、关键定义（原文/权威表述）
- **XX**：<出处> 的表述是「……」
- **YY**：<出处> 的表述是「……」

## 三、关键数字
| 指标 | 数值 | 口径 | 时点 | 来源级别 |
|---|---|---|---|---|

## 四、机构与文件
- <机构全名>（成立年份，职能）

## 五、易混概念对照
| 常被混淆 | 区别 | 一句话辨析 |
|---|---|---|

## 六、本模块"不确定就别写"清单
- 具体条文编号
- 具体票数/席位数
- 五年以前的统计数字
- ……

## 七、资料来源
（按下面第三节的分级标注）
```

## 三、资料来源分级

| 级别 | 类型 | 可用于 |
|---|---|---|
| **A** | 官方原始文件、法律法规原文、国际组织统计、学术专著 | 任何断言 |
| **B** | 权威媒体、专业词典/年鉴、教科书 | 一般断言 |
| **C** | 高质量大众读物、纪录片、知名科普 | 仅用于背景与案例 |
| **D** | 社区、博客、个人经验 | **不作为事实依据**，只可作为"观察样例"并注明 |

**规则：**
- 涉及**数字与条文**的断言，必须 A 级或 B 级。
- 只有 C 级来源的，**把断言降级为"一般认为""多数资料显示"**，不写成定论。
- **没有来源的，不写。**

> ⚠️ 现实约束：写作 agent 通常**不能联网**。因此"来源分级"不是写作时查，而是**写之前由人或可联网的一步先核实好，落到基线文件里**。基线文件里没有的硬事实，卡片一律不写。

## 四、写作时的三条铁律

### 铁律一：只引用基线，不自行生成

卡片里出现的年份、数字、条文、机构名，**必须能在本模块的 `事实基线.md` 里找到**。
基线里没有的 → 两种处理：
1. 改写成不含硬事实的表述（"较早出现""多数国家"）
2. 整句删掉

### 铁律二：不确定就删，绝不换一个"看起来合理"的顶上

这是 agent 最常见的失败模式：**删掉一个错数字，顺手补一个同样没根据的数字。**
明确禁止。宁可这一句不见，不要这一句变假。

### 铁律三：跨卡片自洽

同一个事实（比如"某法通过于某年"）在多张卡片出现时，**必须一致**。
写完一个模块，跑一遍冲突检查。

## 五、三类高危事实（重点盯防）

| 类型 | 例子 | 为什么容易错 |
|---|---|---|
| **数字与统计** | GDP、人口、比例、价格 | 记成旧年份；口径不同（名义/实际、全国/城镇） |
| **条文与编号** | 法律第 X 条、标准编号、条款名 | 修订后编号会变；易与相邻条款混 |
| **机构与职务** | 机构全名、成立年份、职能归属 | 简称与全名混用；机构改组后名称变化 |

**其他高危项**：人名译名不一致、地名变更、品牌归属变更（被收购）、产品参数代际混淆。

## 六、校验

每个模块写完后跑：

```bash
python3 tools/verify_cards.py
```

检查项：
1. 八段结构齐全
2. 卡片字数落在层级区间
3. 卡片里出现的年份/数字，是否能在该模块 `事实基线.md` 找到（粗匹配）
4. 模块索引与实际文件一致

**但这只是机器能查的。** 真正确认「说得对不对」，仍然需要**一轮独立审稿**——审稿 agent 只报告不改文件，主 agent 统一修订。

---

## 七、一次完整的写作流程

```
① 写模块导读（3000 字）        ← 先想清楚这个领域的地图
② 写事实基线（硬事实清单）      ← 需要时可联网核实
③ 按基线写卡片（每卡 8 段）
④ 跑 verify_cards.py           ← 结构 + 字面一致
⑤ 派独立审稿 agent             ← 只出问题清单
⑥ 主 agent 逐条修订
⑦ 再跑校验 → 更新 README → 提交
```

**② 和 ⑤ 是这一步最容易省略、也最不能省的。**
